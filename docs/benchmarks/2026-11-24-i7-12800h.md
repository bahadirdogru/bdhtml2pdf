# bdhtml2pdf 0.1.3 (pre-release) against five engines on an i7-12800H, 2026-11-24

The five-engine comparison for release 0.1.3, on the same i7-12800H laptop
and with the same engines, system packages and fonts as the 0.1.2 run
([2026-11-23-i7-12800h.md](2026-11-23-i7-12800h.md)): Fedora 45, mains
power, `throughput-performance` tuned profile, `performance` governor,
10 runs per fixture. The run started at 01:16 local time (UTC+3), so the
Environment section below shows 2026-11-23 in UTC.

bdhtml2pdf is **the published release binary**, not a local build:
`bdhtml2pdf-0.1.3-linux-x86_64.tar.gz` from the GitHub release (sha256
checked against its `.sha256` file), built by the release workflow with
`opt-level = 3` (fulgur `31f572d2`, Blitz `c13cfe7d`, as pinned in
`.github/upstream.env`). This is the file users download. The other
engines are the ones listed in the 0.1.2 run.

Everything below the line is the unedited output of:

```sh
BD=…/bdhtml2pdf-0.1.3-linux-x86_64/bdhtml2pdf SGH=… WK=… CHROME=chromium-browser WEASY=…/weasyprint bench/run.sh -n 10
BD=… SGH=… WK=… CHROME=chromium-browser WEASY=…/weasyprint bench/security.sh      # 40 s / 2 GB per run
```

## Changes since 0.1.2

- **opt-level 3 instead of `"s"`.** The JavaScript-heavy fixtures are about
  10% faster: React 0.164 → 0.148 s, Vue 0.157 → 0.142 s, the 1000-row
  invoice 0.163 → 0.149 s. The pages without a framework gain 1–8 ms
  (0.07–0.10 s). The JavaScript memory bomb (`dos-memory`) reaches the
  memory limit in 3.7 s instead of 5.4 s.
- **The cost:** the binary is 29 MB instead of 22 MB, and the largest
  process's RSS is about 3 MB higher (the bigger binary's resident pages;
  34.6 instead of 31.1 MB for `modern-css`). The cgroup peak, which counts
  only memory the conversion allocates, is unchanged.
- **No regressions.** Every correctness score, every PDF (pages, size,
  fonts) and every security verdict is the same as in the 0.1.2 run.

## Notes on this run

- **Correctness is read from the last of the 10 runs.** Chromium's
  `modern-js` is 18 or 19 of 19 from run to run (headless Chromium fires
  `requestAnimationFrame` only when it produces a frame); it was 19 here
  and 18 in the 0.1.2 run.
- The other engines' times and memory are within ±3% of the 0.1.2 run, so
  the machine behaved the same in both runs.
- The notes of the 0.1.2 run on fonts, install size, page size, security
  timings and the ✅ of engines without JavaScript apply here too.
