# bdhtml2pdf 0.1.1 (pre-release) against five engines on an i7-12800H, 2026-11-22

The same five-engine comparison as [2026-11-22.md](2026-11-22.md), on a
second machine: an i7-12800H laptop with Fedora 45, on mains power with the
`throughput-performance` tuned profile (`performance` governor), 10 runs
per fixture. The i7-6700 run stays the comparison to quote; this file shows
how the numbers move on a faster machine with other system packages and
fonts.

bdhtml2pdf is built from `b776e64` (fulgur `19aa3185`, Blitz `c13cfe7d`, as
pinned in `.github/upstream.env`). The other engines:

| Engine | Version | From |
|---|---|---|
| sghtmltopdf | 0.8.0 | `cargo install sghtmltopdf --version 0.8.0 --locked` |
| wkhtmltopdf | 0.12.6.1 (with patched qt) | the official `wkhtmltox-0.12.6.1-3.almalinux9.x86_64.rpm` (sha256 `357a587c…03524b`), unpacked with `rpm2cpio … \| cpio -idm` |
| Chromium | 157.0.8103.78 | the Fedora 45 package |
| WeasyPrint | 70.0 | `pip install weasyprint==70.0` in a virtualenv (Python 3.15) |

Everything below the line is the unedited output of:

## Notes on this run

- **Time.** Every engine is faster than on the i7-6700: bdhtml2pdf takes
  0.07–0.10 s for the fixtures without a framework (0.14–0.22 s there) and
  0.16–0.17 s for React, Vue and the 1000-row invoice (0.30–0.35 s
  there). wkhtmltopdf gains least, about 15–30 %.
- **Power profile matters.** A run two hours earlier on battery with the
  `balanced-battery` profile (`powersave` governor), at fulgur `63dd6908`,
  was about twice as slow for most engines: bdhtml2pdf 0.15–0.21 s for the
  fixtures without a framework. Memory and scores were the same. That run
  is not kept.
- **Correctness is the same as on the i7-6700 except on `fonts.html`.**
  Chromium's `modern-js` is 18 or 19 of 19 from run to run (see the note
  in [2026-11-22.md](2026-11-22.md)); it was 19 here.
- **`fonts.html` depends on the system fonts.** bdhtml2pdf and Chromium
  8/8 on both machines. wkhtmltopdf 6/8 here (5/8 there): it passes the CJK
  check with this machine's fonts. WeasyPrint 7/8 here (8/8 there): it
  fails the Arabic check. sghtmltopdf 7/8 on both, but here it takes 1.2 s
  and writes a 19 MB PDF (0.08 s and 35 KB there), with one font embedded
  whole instead of as a subset; the 2026-11-19 run on this machine showed
  the same, from the CJK fallback font. WeasyPrint also takes 1.4 s and
  169 MB on this fixture.
- **Install size.** wkhtmltopdf is 39 MB from the AlmaLinux 9 package
  (44 MB from the Debian one). Chromium is `/usr/lib64/chromium-browser`.
  WeasyPrint is its virtualenv; Python and Pango from the system are not
  counted.
- **Page size.** Chromium prints Letter, the others A4, so page counts differ.
- **Security times are single runs,** not medians. Every verdict is the
  same as on the i7-6700.
- **sghtmltopdf's and WeasyPrint's ✅ on the JavaScript cases** only reflect
  that they have no JavaScript.
